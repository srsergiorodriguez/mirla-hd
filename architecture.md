# Mirla Architecture — The Structural Map

> Status: planning (no implementation yet). Branch: `agent-dev`.
> Last reviewed: 2026-10-26.

This document defines **where things go**, **who owns what**, and **how the pieces talk to each other**. It is deliberately stricter than the current code: the goal is to make the existing system easier to change without changing how it looks or what it does.

---

## 1. What Mirla is

Mirla is not a single application. It is a **build-time pipeline plus a runtime presentation layer** that runs on top of Publii:

| Piece | Runtime | Role | Owns |
|---|---|---|---|
| **Publii** | Desktop app (Electron/Node) | Build orchestrator, content editor, static renderer | Site database, pages, menus, media, theme/plugin loading, output |
| **Mirla plugin** | Node (inside Publii, build time) | Collection compiler | CSV/image ingestion, validation, data payload, item pages, catalog markup, health report |
| **Mirla theme** | Handlebars + CSS + browser JS | Presentation shell | Page templates, design tokens, print templates, global scripts |
| **Svelte web components** | Browser (runtime) | Interactive collection UI | Exploration, visualization, item previews, tables |
| **Mirla Data Editor** | Browser (offline, pre-build) | Authoring tool | Protocol/metadata editing, image pairing, CSV/ZIP export, project JSON |
| **Paged.js + p5.js layer** | Browser (print preview) | Crossmedia output | Paginated zines and (planned) print catalogs |

There is **no custom backend server**. The plugin is the "backend" only in the sense that it runs at build time. The website is fully static.

### Important facts about this layout

1. **The plugin source is not what Publii loads.** Publii loads `~/Documents/Publii/plugins/mirlaPlugin/`, not `mirla-hd/mirlaPlugin/`. Today they are identical copies, which is the duplication we want to remove. The fix is documented in §7.
2. **`input/themes/mirlaTheme/` is currently both the site theme and the release source.** GitHub Actions zips it directly. This works, but it means a developer is always editing the live site theme. Do not move it without a migration plan.
3. **`assets/css/style.css` is generated by Publii** (`theme-variables.js` + `main.css` + overrides + custom CSS) and is tracked only as a placeholder. Never edit it by hand.
4. **`assets/js/mirla-components.js` is generated by Vite.** Never edit it by hand; rebuild from `svelte-components/`.
5. **`input/themes/mirlaTheme/zine.js` is stale.** The template loads `assets/js/zine.js` via `{{js "zine.js"}}`. The root copy should be deleted in a cleanup task, after confirming no external references.
6. **`input/config/plugins/Mirla.json` is stale/unused** (capital `M`). The active site config is `mirlaPlugin.json`. The stale file mentions a `galleryFilters` option that is not in `plugin.json` and is not emitted by the plugin.

## 3. Boundaries

### 3.1 Plugin ↔ data contract (hard boundary)

The plugin is the **only** component allowed to:

- read `input/media/files/collection/**`;
- parse `Protocol*.csv` and `Metadata*.csv`;
- validate types, references, duplicate PIDs;
- map PIDs to image files/folders;
- write `collection.json`, `collection-data.js`, `item/<pid>/index.html`, catalog markup, and `mirla-report.txt`.

The plugin must **not** know about CSS, Svelte components, or page layout beyond the small item/catalog HTML fragments it injects.

The contract is described in §4. It is the API between the plugin, the theme, and the components. Changes to it require updating `testing.md` fixtures and both consumers.

### 3.2 Theme ↔ components

The theme:

- renders Handlebars pages;
- injects `window.MIRLA_CONTEXT` and the collection payload script;
- loads the component bundle;
- provides global design tokens in `assets/css/main.css`;
- owns print templates and print CSS.

The Svelte components:

- read the payload and context;
- render interactive UI;
- own local state only;
- **must not** fetch collection data, mutate the payload, or assume Publii APIs exist.

### 3.3 Components ↔ each other

There is **no shared runtime store**. Each custom element is independent. The current `ItemsBar` is a local child of the visualization components.

If cross-component coordination becomes necessary (e.g., "click a chart bar to filter the index"), use a documented DOM event on `document`:

```js
document.dispatchEvent(new CustomEvent('mirla:filter', {
  detail: { key: 'medio_impresion', value: 'Offset' }
}));
```

Do not introduce a global mutable store or a singleton module that owns collection state. The payload is immutable for the page lifetime.

### 3.4 Data editor ↔ everything else

The editor is an **offline authoring tool**. It communicates only through files:

- imports/exports `Protocol*.csv`, `Metadata*.csv`;
- exports `images/**` and `_thumb.webp` files;
- saves/loads a project JSON (tables only; images are not persisted);
- produces a ZIP that the user extracts into `input/media/files/collection/`.

It must not call Publii, the plugin, or the live site. Its output must remain byte-compatible with the plugin's CSV expectations (BOM handling, headers, escaping, WebP/thumbnail naming).

### 3.5 Print / crossmedia

Print is a **theme concern** with **plugin-generated static content**:

- `page-print.hbs` remains the zine template;
- a new `page-catalog.hbs` (planned) will be the catalog template;
- the plugin replaces a `[MIRLA_CATALOG]` placeholder in that page's rendered HTML (via an `htmlOutput` modifier) with static item cards;
- Paged.js handles pagination, running headers, and page numbers in the browser;
- no client-side fetch of collection data is required for print.

This keeps print robust: the HTML leaving Publii already contains the catalog.

## 4. Data contract (v1)

### 4.1 `collection.json` / `collection-data.js`

`collection.json` is written to `output/media/files/collection/collection.json`.
`collection-data.js` contains the same object assigned to `window.MIRLA_COLLECTION_DATA`.

Shape:

```json
{
  "protocol": {
    "pid":   { "type": "pid",   "description": "Identificador único" },
    "label": { "type": "label", "description": "Nombre visible" },
    "autores": { "type": "text", "description": "..." },
    "medio_impresion": { "type": "ref:Tecnica", "description": "..." }
  },
  "items": [
    {
      "pid": "4530labezaca_lp4ufkpzjg",
      "label": "45-30",
      "autores": "Base-v, Antihéroe, ...",
      "medio_impresion": { "pid": "tec-offset", "label": "Offset", "images": [] },
      "images": ["https://example.org/media/files/collection/images/4530labezaca_lp4ufkpzjg.jpg"],
      "thumb": "https://example.org/media/files/collection/images/4530labezaca_lp4ufkpzjg_thumb.webp",
      "_collection_type": "Tecnica"
    }
  ]
}
```

Rules:

- `protocol` is a dictionary keyed by attribute name. `type` casing is preserved (e.g. `ref:Tecnica`).
- `items` includes **main-table items first**, then one item per row of each secondary table. Secondary items carry `_collection_type`.
- `images` is always an array of absolute URLs (may be empty). `thumb` is a URL or `null`.
- `ref` values are a string (single ref) or an array of strings (multiple refs). This is a current quirk; consumers must handle both.
- `ref:Table` values are a string or array of stub objects `{ pid, label, images }`. If the target is missing, the current plugin falls back to the raw pid string.
- All other values are strings, numbers, or booleans as produced by PapaParse `dynamicTyping`.
- `pid` is always a string.
- There is no `schemaVersion` yet. Adding one is a planned, backwards-compatible addition (`schemaVersion: 1`); consumers must tolerate its absence.
- Protocol attributes starting with `_` are internal by convention; components hide `_` keys from public tables.

### 4.2 `window.MIRLA_CONTEXT`

Injected by the theme:

```js
window.MIRLA_CONTEXT = {
  siteDomain: "https://example.org/",
  mediaUrl: "https://example.org/media/files/",
  i18n: {
    searchPlaceholder, resultsFound, loading, all,
    downloadCSV, clearSearch, noRecordsFound, collectionMetadata
  }
};
```

- `siteDomain` is used to build item URLs (`{siteDomain}item/{pid}/index.html`). Keep the trailing slash convention consistent.
- Components must fall back gracefully if the context or i18n keys are missing.
- The context script is currently duplicated in `page.hbs`, `page-interactive.hbs`, and `post-interactive.hbs`. It should become a single partial (planned).

### 4.3 File/CSV contract

- Main tables: `Protocol.csv`, `Metadata.csv`.
- Secondary tables: `Protocol_<Suffix>.csv`, `Metadata_<Suffix>.csv`.
- Protocol headers: `Attribute`, `Type`, and optionally `Description` (the plugin also accepts `Descripción`, `descripcion`, `description`).
- Metadata headers must match protocol attribute names exactly (case/space sensitive).
- UTF-8 BOM is stripped on read. Exports include a BOM.
- `pid` and `label` are required for every row.
- Duplicate main PIDs are fatal.
- Images: single file `<pid>.<ext>` or folder `images/<pid>/`; supported extensions: jpg, jpeg, png, webp, gif, svg. `_thumb.webp` / `_thumb.jpg` are optional thumbnails.
- Other media paths in metadata are relative to `input/media/files/collection/` (not the `images/` folder).

## 5. State and event flow

### 5.1 Build-time flow (full render)

```text
Publii render start
  → beforeRender
  → render pages/posts (theme HBS)
       → htmlOutput modifier (plugin):
            if output contains [MIRLA_CATALOG]:
                lazily parse dataset (cached)
                replace placeholder with static catalog HTML
  → copy media/assets/plugins
  → afterRender event (plugin):
       parse dataset (or use cached)
       write collection.json + collection-data.js
       generate item/<pid>/index.html from the compiled item template page
       write mirla-report.txt
  → Publii finishes
```

Key points:

- The plugin currently does all parsing in `afterRender`. The catalog needs data **during** page rendering, so parsing must be extracted into a cached `getDataset(rendererInstance)` method callable from both the modifier and `afterRender`.
- `afterRender` also runs for single-page previews. In that mode only one page may exist in `output/`; the plugin must **skip missing template pages with a warning**, not throw (planned).
- Publii `require`s `plugins/<name>/main.js` and caches it. Restart Publii (or the app's renderer) after changing plugin code.

### 5.2 Browser/runtime flow

```text
Page loads
  → theme injects MIRLA_CONTEXT
  → collection-data.js defines MIRLA_COLLECTION_DATA
  → mirla-components.js registers custom elements
  → each <mirla-*> upgrades and reads the globals
  → local interaction state (search/filter/selection) stays inside the element
```

No runtime data fetching is allowed for collection data. The only current exception is `MirlaMap`, which fetches world geometry from `unpkg.com`. This is a known offline/privacy risk; it should be self-hosted later (out of scope for the first phases).

### 5.3 Editor state

- A single in-memory `state` object (`activeTab`, `tabs`, `data[tab].protocol`, `data[tab].metadata`) plus two image maps (`File` objects and preview data URLs).
- Persisted only when the user exports project JSON or the collection ZIP.
- Images are intentionally not serialized into project JSON (browser File objects cannot be saved); the current UX asks the user to re-drop the images folder. Preserve this behavior in the port.
- No localStorage/sessionStorage is used today. Do not add implicit persistence without a user-visible decision.

## 7. Development loop: one codebase for the plugin

### Target

`~/Documents/Publii/plugins/mirlaPlugin` becomes a **symlink** to `mirla-hd/mirlaPlugin`. Publii then loads the exact source used by GitHub Actions; there is no copy to keep in sync.

### Why this is expected to work

From Publii 0.47.5:

- `appDir` is `~/Documents/Publii`.
- The plugin loader uses `fs.readdirSync(appDir/plugins)` and `fs.statSync(path).isDirectory()`, which follow symlinks.
- The renderer loads the plugin with `require(path.join(appDir, 'plugins', pluginName, 'main.js'))`, and Node resolves symlinks to the real path.
- Plugin asset reads use `__dirname` inside the real plugin folder, so `osd_icons/` and `item-template.html` resolve correctly.
- The site-specific settings file remains `input/config/plugins/mirlaPlugin.json`; it is not inside the plugin folder.

### Procedure (to be executed only after approval)

```bash
# 1. Inspect
PLUGIN_SRC="$HOME/Documents/Publii/sites/mirla-hd/mirlaPlugin"
PLUGIN_DST="$HOME/Documents/Publii/plugins/mirlaPlugin"
test -d "$PLUGIN_SRC" && test -d "$PLUGIN_DST"

# 2. Back up the installed copy (do not delete it)
mv "$PLUGIN_DST" "$PLUGIN_DST.bak-$(date +%Y%m%d-%H%M%S)"

# 3. Link
ln -s "$PLUGIN_SRC" "$PLUGIN_DST"

# 4. Verify
ls -la "$HOME/Documents/Publii/plugins/"
test -f "$PLUGIN_DST/main.js"
```

Then restart Publii, open the site, confirm the plugin is listed/enabled, run a preview, and check `input/media/files/collection/mirla-report.txt`. Rollback: remove the symlink and rename the backup back.

### Rules

- Never run the link script with a wildcard or an unverified destination.
- The installed backup stays until the symlink has survived one full preview + one full publish.
- On Windows, use a directory junction (`mklink /J`) or a sync script; a plain copy reintroduces drift.
- Publii caches `require`d plugins. Restart the app after plugin changes; a preview alone is not guaranteed to reload the module.
- GitHub Actions must zip `mirla-hd/mirlaPlugin` directly. No copy step.

### Fallback (if symlinks are unacceptable)

Add `scripts/sync-plugin.sh` with an explicit source/destination and a `--watch` mode (rsync), plus a CI check that the installed copy is identical. This is second choice: it still duplicates bytes, but removes manual copying.

## 8. Build and release pipeline

Current workflow (`.github/workflows/build-and-release.yml`):

1. On tag `v*` or manual dispatch.
2. Zip `input/themes/mirlaTheme` → `mirlaTheme.zip`.
3. Zip `mirlaPlugin` → `mirlaPlugin.zip`.
4. Upload `MirlaDataEditor.html`.
5. Create/update GitHub release.

Planned changes:

- Run tests before packaging.
- Build the Svelte components into the theme before zipping.
- Build the data editor from `data-editor/` before uploading.
- Exclude `.DS_Store`, `node_modules`, and generated `assets/css/style.css` from the zips.
- Add a CI workflow for branch pushes/PRs (tests + builds, no release).
- Keep the release asset names stable (`mirlaTheme.zip`, `mirlaPlugin.zip`, `MirlaDataEditor.html`).

## 9. Known constraints and debt

These are recorded here so future changes do not silently break them:

1. **Plugin is a single 555-line CommonJS file.** Parsing, validation, media resolution, HTML rendering, and file writing are interleaved. It has no tests and injects CSV values into HTML without escaping.
2. **Theme context script is duplicated** in three templates.
3. **`zine.js` exists twice**, and the root copy is stale.
4. **Font configuration is manual**: four text fields requiring the user to extract Google Fonts URL segments.
5. **Print CSS is inline** in `page-print.hbs` and hardcodes fonts/page size.
6. **Catalog does not exist**; the crossmedia workflow only prints an authored page (zine).
7. **Data editor is a single 1,313-line HTML file** with CDN dependencies, inline styles, and imperative DOM code.
8. **Generated artifacts are tracked**: `assets/css/style.css` and `assets/js/mirla-components.js`. CI must rebuild them; humans must not edit them.
9. **Runtime CDN dependencies**: Pico, Shoelace, Google Fonts, OpenSeadragon, unpkg world atlas. Offline workshops need network unless these are self-hosted.
10. **SEO of item pages**: generated item pages keep the template page's canonical URL and are not in the sitemap. Not in the current scope, but worth a later task.
11. **Plugin report is written into the input collection folder**, so a build modifies the source tree. Consider moving it to `output/` in a later cleanup.
12. **Docs drift**: `README.md`, `svelte-components/README.md`, and `DesarrollarComponentes.md` disagree on prop names (`date-key` vs `datekey`) and plugin options (`galleryFilters`). Fix during the relevant phase.
13. **Duplicate DOM IDs** in components (`mirla-search-input`, `mirla-table-search`) if multiple instances are on one page.
14. **Map component fetches world geometry from unpkg** at runtime.
15. **Editor ZIP filename differs by language** (`collection.zip` vs `Mirla_Collection.zip`).

## 10. Architecture decisions (ADR log)

| ID | Decision | Rationale | Status |
|---|---|---|---|
| ADR-001 | Keep Publii as the build orchestrator; no custom server | Static output, workshop-friendly, no hosting requirements | Accepted |
| ADR-002 | Use read-only global payloads (`MIRLA_COLLECTION_DATA`, `MIRLA_CONTEXT`) as the runtime contract | Zero coupling, works with static pages, no build step in the browser | Accepted |
| ADR-003 | Symlink the plugin source into `~/Documents/Publii/plugins`; CI zips the same source | Removes duplicated code | Proposed (awaiting approval) |
| ADR-004 | Generate the print catalog in the plugin via an `htmlOutput` modifier into a theme print page | Static, previewable, no extra app, integrates with Publii | Proposed |
| ADR-005 | Port the data editor to Svelte only if a single-file/file:// spike passes | Avoids an unmaintainable rewrite; preserves distribution model | Proposed |
| ADR-006 | Semantic tokens live in the theme; components use `var(--mirla-*, fallback)` | Single runtime source of truth; components still work in isolation | Proposed |
| ADR-007 | Keep public custom-element names and props unchanged during the design-system refactor | No breaking change for existing sites/workshops | Accepted |

## 11. Non-goals (for the first implementation cycle)

- Rewriting Publii or replacing it.
- Introducing a database or server-side runtime.
- Changing the visual identity of the site.
- Adding user accounts, analytics, or a CMS UI inside the components.
- Full offline bundling of every CDN dependency (separate later task).
- Building a general-purpose print engine beyond Paged.js.
